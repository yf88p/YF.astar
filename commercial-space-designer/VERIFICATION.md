## Real Browser Workflows

The production browser run performed ordinary UI actions for these operations:

- Opened the furnished cafe in linked view; selected and numerically extended its wall; checked shared endpoints, unchanged hosted openings, the analytical new area, budget updates, undo, and redo.
- Added a door and elevated window with the plan tools. Raycast the **actual scene meshes** through both holes and below the window. Entered real pointer lock and moved the actual first-person camera through the open doorway using keyboard frames.
- Closed the door in its inspector, attempted the same motion, and verified the camera stopped before the wall. Attempted traversal at the window and verified it remained blocked.
- Moved a table into the defined door clearance region, inspected the actual warning, and moved it clear. Completed a pointer drag and verified a single undo restored the full starting arrangement.
- Selected the table by actual Three.js raycasting and checked the linked plan selection and numeric inspector.
- Changed floor/wall materials and daylight, saved a camera, duplicated an alternative, changed its finish, checked baseline isolation, and opened the budget-delta comparison.
- Deleted a wall with attached openings through the confirmation dialog and restored all attachments with undo.
- Exported project JSON, reloaded local autosave, rejected malformed JSON without replacement, reimported the valid file, and compared the complete project.
- Downloaded SVG, CSV, and an actual current-scene PNG. The PNG was generated by WebGL capture, not by the browser screenshot helper.
- Constructed a closed 6 x 5 m room from the blank path, checked 30 m2, and placed catalog furniture.
- Opened both other furnished examples, checked mobile overflow at 390 x 844, and opened the actual mobile numeric wall inspector.

For the exact isolated numerical fixture, the harness loaded a small validated document through the diagnostic fixture loader. It then used the UI schedule to verify **18.000 m2** for the two costed faces, probed the actual 1 x 2 m door / 1 x 1 m window meshes, checked the solid sill, and traversed the 1 x 2 m doorway using the application's real keyboard motion/collision loop. Fixture loading and reproducible camera positioning are explicit automation aids, not substitute collision implementations.

The initial browser runs found two pointer-lock issues: a spurious first mouse delta and Escape behavior under synthetic input. The implementation now ignores the first lock-transition delta and explicitly releases pointer lock on Escape. The complete workflow was rerun successfully after these fixes.

## Performance Measurement

**Environment:** Chromium 153.0.8010.12, headless, ANGLE SwiftShader **software** WebGL; AMD Ryzen 7 5825U host, 16 logical CPUs, 12 GB reported memory; Linux on a shared host. Browser viewport 1440 x 1000, device pixel ratio 1. No hardware-GPU performance claim is made.

**Visible workload:** 40 wall segments forming a 30 x 30 m layout and 100 physical furniture instances, all placed within the camera's visible scene. The camera shows the complete layout. Boundary cutaway leaves the affected wall plinths visible; no furniture is hidden for measurement.

| Metric                                 | Observed production result         |
| -------------------------------------- | ---------------------------------- |
| Scene triangles                        | 120,970                            |
| Main-pass draw calls                   | 23                                 |
| GPU geometries                         | 65 before and after repeated edits |
| GPU textures                           | 5 before and after repeated edits  |
| Sampled rendered-frame intervals       | 60                                 |
| Median frame interval                  | 128.4 ms                           |
| 95th percentile frame interval         | 269.7 ms                           |
| Observed interval range                | 13.4-402.5 ms                      |
| Ten model-to-scene rebuild samples     | 8.4-21.7 ms                        |
| Browser-driven edit/commit round trips | 45.3-100.2 ms                      |

Frame intervals are consecutive `requestAnimationFrame` intervals during actual rendering, not model-only timings or a browser refresh-rate estimate. The software renderer is **not smooth at this stress workload**; the approximately 7.8 FPS median-equivalent result is disclosed rather than claimed as 60 FPS. DOM editing remained responsive at the measured round-trip times. These figures include shared-host contention and must not be generalized to a dedicated hardware GPU.

Repeated catalog parts are merged by material and instanced across furnishings. This reduced the same scene from 384 to 23 draw calls, but software rasterization remained the main observed bottleneck. Wall/floor geometries, instance buffers, selection geometries, and dynamic light materials are disposed when replaced. Catalog geometry and the finite procedural finish palette are intentionally cached. Shadow maps update on model changes rather than being rebuilt for every orbit frame.

## Reproducing Evidence

`npm run verify:browser` writes these generated artifacts to `verification/`:

- `report.json`: browser, hardware, scene counts, individual rebuild/round-trip samples, frame statistics, assertions, errors.
- `desktop.png`, `mobile.png`, `boutique.png`, `exhibition.png`, `presentation.png`, `stress.png`: actual browser screenshots of the working UI and scene.
- `scene.png`: **application-exported WebGL image** of the current altered design.
- `project.forma.json`, `plan.svg`, `schedule.csv`: downloads from the application's real export menu.

Generated artifacts are gitignored but retained locally after verification. The test suite and harness are tracked and can regenerate them. The headless harness does not prove every possible arbitrary layout or GPU/browser combination; numerical tolerances and supported geometry restrictions are documented in the README.
